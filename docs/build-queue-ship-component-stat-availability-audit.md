# Build Queue Ship Component Stat Availability Audit

Date audited: 2026-07-26

Scope: ship weapons, power plants, quantum drives, coolers, and shields shown by the Build Queue component-statistics UI. The availability tables capture the pre-implementation data-path audit; the production implementation status is recorded below.

The audit evaluates the working tree as it existed on 2026-07-26. It is archival evidence; current ownership and runtime instructions are maintained in [the API and data-flow runbook](api-data-flow-runbook.md) and [the crafting handoff](crafting-browser-detail-handoff.md).

## Executive finding

The missing ship-weapon statistics are primarily a delivery problem, not a lack-of-data problem.

- The authoritative LIVE registry has broad weapon coverage: penetration and projectile data on 191 of 193 records, spread on 187, fire rate and heat-per-shot on 188, energy-ammo regeneration on 120, and full overheat/recovery data on 65.
- The AD5B specifically has penetration, all five spread values, and all seven thermal/overheat recovery values in the LIVE registry.
- The fitting API already carries most of those fields, and the current working-tree projection has rows for most of them.
- A smaller set is still dropped because source and public field names do not match, or because the public contract does not expose the field.
- Core components have the same problem. Quantum fuel, drive calibration/acceleration, cooler power-pip curves, shield downed delay, and several repair/signature fields are populated but do not reach the card.

The correct implementation direction is to complete the shared fitting detail contract and projection. Production calculations should not be recreated in the Build Queue component.

## Production implementation status

Implemented on 2026-07-26:

- Added zero-safe canonical `quantumFuelRequirement` delivery while retaining `fuelRate` as a compatibility alias.
- Added shared-boundary aliases for weapon burst size and penetration near/far radii.
- Exposed quantum calibration values, derived calibration time, and both acceleration stages.
- Exposed cooler thermal equalization and a shaped, allowlisted power-pip cooling curve.
- Exposed shield downed regeneration delay and rendered the shield regeneration power curve.
- Completed resource-component distortion maximum and repair-stat projection without conflating distortion maximum with distortion resistance.
- Rendered subtype-applicable weapon action fields, energy maximum load, recharge rate, recharge cooldown, spread, penetration, and thermal recovery.
- Added deterministic Build Queue coverage for AD5B, M5A, FR-66, Atlas, SnowBlind, and JS-300 at both required desktop resolutions.

Follow-up on 2026-07-27:

- Normalized quantum-drive display units through shared helpers used by component cards, Crafting, Fitting, and Build Queue.
- Invalidated legacy persisted fitting-component records after the response contract expanded and added cache regression coverage.
- Prioritized Alpha Damage in weapon summaries while removing redundant unmodified damage-channel rows when the total is present.

The public fitting response remains additive API v1; existing consumers can continue reading the legacy quantum fuel alias.

Still unavailable:

- Ship-weapon damage falloff and impulse falloff remain blocked on an authoritative ammunition join. The current LIVE vehicle-ammunition source contains no `BulletDamageDropParams` or `BulletImpulseFalloffParams` records to map. No UI fallback or inferred calculation was added.
- Null ship-weapon distortion resistance and IR signature remain unavailable rather than being relabeled from unrelated fields.

## CQ7 follow-up

CQ7 is an FPS weapon, not a ship weapon, and therefore does not use `ship_weapons.json`.

The current local by-id card for `CQ7 Rifle` is now populated from the Foundry weapon -> magazine -> ammo chain. It includes fire mode/rate, burst size, ammo capacity, projectile values, physical damage, DPS, hip-fire spread, damage falloff, impulse falloff, heat/wear, penetration radii, and attachment ports.

The CQ7 Build Queue path fetches the by-id card, so that enriched record is the relevant detail source. The compact `browse.json` record still contains only FPS weapon identity and must not be used as the detail-stat contract.

## Data and semantic cautions

- `projectileMaxTravel` and `calculatedRange` are derived from speed and lifetime; they are not automatically an effective combat range.
- `theoreticalDps`, `sustainedDps60`, `damageOver60Seconds`, `calibrationTime`, and `selfRepairBaselineHp` are derived fields and should remain labeled or documented as such.
- Signature values are populated, but several provenance records identify their unit confidence as low. Do not add an unverified unit.
- Zero is a valid value. UI filtering must distinguish zero from missing.
- Power-pip arrays are subtype/system data, not ordinary scalar card rows. They need a compact curve or allocation-aware presentation.
- Null distortion resistance or IR data must remain unavailable; no frontend fallback should relabel EM/radar or another resistance as the missing stat.
